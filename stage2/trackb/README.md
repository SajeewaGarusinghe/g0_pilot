# Track B spike — Online Boutique on k3d behind a current OpenTelemetry collector

G0 stage 2, **step 10**. The question the build guide asks is a yes/no: can this project stand up
its own instrumented deployment, collect its telemetry through a collector it controls, and convert
that into the case layout RCAEval's methods and this project's rules read? Track B is the arm with
*enforced provenance*, so if the answer is no, R2 has nowhere to go once `NA_STATUS_LOSSY` rules out
Train Ticket.

`STATUS.md` says to **start with K18**: that a gRPC status code survives `rcaeval-convert`. That is
answered first and separately, because it needs no cluster — see `../k18_otlp_status.py`.

## What this directory is

| File | What it does |
|---|---|
| `00-install.sh` | Installs docker, kubectl and k3d, pinned, idempotent. Oracle Linux 9 |
| `01-cluster.sh` | Creates the k3d cluster (1 server, 2 agents, traefik disabled) |
| `collector.yaml` | The collector: a **current** release (0.165.0), OTLP in, `file` exporter writing OTLP/JSON out — one `ExportTraceServiceRequest` per line, which is what `rcaeval-convert traces` reads |
| `02-deploy.sh` | Applies the collector and Online Boutique v0.9.0, then switches tracing on |
| `03-capture.sh` | Waits for every rollout, records the deployment, lets the load generator run, copies the collector's file out |
| `04-convert-and-check.py` | Runs the real `rcaeval-convert traces` and measures the result the way steps 1–3 measured RE2-OB, so the two are comparable |

## Running it

```bash
bash stage2/trackb/00-install.sh                 # once; needs sudo
bash stage2/trackb/01-cluster.sh

# the application manifest is upstream and is fetched separately, because this VM cannot
# reach raw.githubusercontent.com (verified 2026-11-14: times out; github.com returns 200)
mkdir -p /home/opc/trackb-upstream && cd /home/opc/trackb-upstream
gh api repos/GoogleCloudPlatform/microservices-demo/contents/release/kubernetes-manifests.yaml?ref=v0.9.0 \
  --jq '.content' | base64 -d > kubernetes-manifests.yaml
# sha256 1a23e5e76be455ebbea50d20aaf3e7b05e3a0b96f7d62af6bf646af4ee958b74

bash stage2/trackb/02-deploy.sh
OUT=stage2/out/step10-<date>/capture WINDOW=420 bash stage2/trackb/03-capture.sh
python stage2/trackb/04-convert-and-check.py --capture stage2/out/step10-<date>/capture
```

Each script re-execs itself under `sg docker` if the shell is not yet in the `docker` group, so no
new login is needed after `00-install.sh`.

To tear the cluster down: `k3d cluster delete trackb`. Docker stays installed.

**What is and is not committed.** This repository ignores `*.jsonl` (see `.gitignore`), so neither
the captured OTLP nor the K18 fixture is in git. Both are reproducible: the fixture is generated
by `../k18_otlp_status.py` on every run, and the capture is regenerated by the scripts above. The
small result tables, the deployment record and the end-to-end check are copied into the knowledge
base at `Msc-project/09-results/g0/trackb-spike/<date>/`, which is where the evidence lives.

## Two things worth knowing before reading the result

**The status-code convention is set by the application, not by the collector.** Online Boutique
v0.9.0's images carry the instrumentation this project already pinned in steps 4–6 — otelgrpc
v0.46.1 (Go), `opentelemetry-instrumentation-grpc` 0.41b0 (Python), `@opentelemetry/…` 0.45.1
(Node) — all of which emit the numeric `rpc.grpc.status_code` that RCAEval's converter reads. The
collector passes attributes through. So deploying v0.9.0 behind a current collector does **not**
trigger K18; rebuilding the services against current OpenTelemetry libraries would. That is a
different and much more avoidable exposure than the known issue first described, and
`04-convert-and-check.py` reports which convention was actually emitted rather than assuming.

**This spike covers traces only.** A full Track B case also needs `metrics.csv` and `logs.csv`:
`rcaeval-convert metrics` wants a Prometheus endpoint, and the target rule that step 8 measured
scores services on `simple_metrics.csv`, whose latency and error columns come from an Envoy sidecar
in the recorded datasets (step 11a, K23). Neither Prometheus nor a service mesh is deployed here.
What that means for Track B is recorded in `09-results/g0/10-trackb-spike.md`, not decided here.
